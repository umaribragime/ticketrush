How TicketRush works,
on one page.

TicketRush is a concert ticketing app built to survive ticket open (티켓 오픈): the moment thousands of fans try to buy a few hundred tickets at the same second. This page is a map of the whole app: what each part does, where it lives, and how a click travels from the browser to the database and back.

1 · Big picture

Three programs work together

The frontend is what you see. The backend holds all the rules (who may buy, how many tickets are left). The database remembers everything. They talk using HTTP requests with JSON.

Solid arrow from the proxy = browser API calls carrying your JWT. Dashed arrow from Server Components = public data fetched server-to-server (no token).

Frontend

What you see

Next.js + React + TypeScript. Pages, buttons, forms, English/Korean, light/dark. It never stores the "truth" — it always asks the backend.

Backend

The rules

Spring Boot + Java 21. Checks the login token, validates input, applies business rules (max 4 tickets, sales window, stock), and saves data.

Database

The memory

PostgreSQL in Docker. Users, events, ticket types, orders, tickets, QR codes, and every gate scan.

    4 · Layers
    
    
    Each part has one job
    
    
    Both apps are split into layers. A layer only talks to the layer below it. This keeps code
      easy to find, test and change — interviewers ask about this a lot.
    
    
    
      
    
        Backend layers (per feature)
        
    
          
    ControllerSpeaks HTTP. Reads JSON, checks input with @Valid, returns JSON. No business rules.
    
          
    ▼ calls
    
          
    ServiceThe use case: "place an order". Runs inside a @Transactional (all steps succeed, or none).
    
          
    ▼ uses
    
          
    EntityData + its own rules: Event.publish(), TicketType.sell(), Order.addTicket().
    
          
    ▼ saved by
    
          
    RepositorySpring Data JPA. Writes SQL for us from method names like findByOrganizerId.
    
        
    
        
    Code is grouped by feature (auth, event, order, ticket, checkin), not by layer —
          everything about "orders" lives in one folder.
    
      
    
      
    
        Frontend layers (Feature-Sliced Design)
        
    
          
    app/Routes = pages. Thin: they only put pieces together.
    
          
    ▼ may import
    
          
    widgets/Big blocks on many pages: header, footer.
    
          
    ▼
    
          
    features/User actions: log in, buy tickets, scan a QR, fill the event form.
    
          
    ▼
    
          
    entities/Business objects: event, ticket/order — their API calls, query keys, badges.
    
          
    ▼
    
          
    shared/No business meaning: HTTP client, UI kit, i18n, formatting, stores.
    
        
    
        
    Rule: imports only go downward. shared never imports from features.

      7 · Backend API
      
    
      All 16 endpoints
      
    
      An endpoint is a URL the backend answers. Try them yourself in Swagger:
      localhost:8080/swagger-ui.html (backend must be running).
      
    
      
      
      
        
      MethodPathWho may callWhat it doesCode
      
        
      
      
    
      
    
      Errors look the same everywhere (RFC 9457 "Problem Details"):
      {"status":409,"code":"TICKET_SOLD_OUT","detail":"Only 0 'VIP' tickets left."}.
      The frontend turns each code into an English or Korean message (err.* keys in shared/i18n).
      
  
      

  
  
      
    
      8 · Data model
      
    
      9 tables and how they connect
      
    
      The schema is written by hand in V1__init_schema.sql and created by Flyway.
      Hibernate only checks that the Java classes match it (ddl-auto: validate).
      
    
      
      
    
      
    
      
      
      Why are prices copied into tickets.price and orders.total_amount?
        If the organizer changes a price tomorrow, old orders must keep the price the fan really paid.
      
      
      Why a random QR token instead of the ticket id?
        So nobody can make a fake ticket by guessing ids. The token is 48 random hex characters.
      
    
      
  
      

  
  
      
    
      9 · Run & test
      
    
      Start it in three steps
      
    
      
      
      1 · Database
        
      cd ticket-rush
docker compose up -d
      
        
      PostgreSQL 17 on port 5434 + Adminer on 8081. Docker Desktop must be open.
      
      
      2 · Backend
        
      cd ticketrush
./mvnw spring-boot:run
      
        
      Or press ▶ on TicketrushApplication in IntelliJ. Port 8080.
      
      
      3 · Frontend
        
      cd frontend
npm install
npm run dev
      
        
      Open http://localhost:3000 (use "localhost").
      
    
      
    
      
      
      Tests
      
        
      Backend — 31 tests (+1 demo) (./mvnw test): they start the real app with
          real security and a real database (H2 in PostgreSQL mode) and call the API like a client. Files: AuthFlowTest,
          EventFlowTest, OrderFlowTest, CheckInFlowTest, AccountFlowTest on H2, plus 3 race tests on real PostgreSQL (Testcontainers, Docker must be running).
      
        
      Frontend — 25 tests (npm test, Vitest): cart rules, date/price formatting,
          form validation, the login form (EN + KO), and "Korean has exactly the same keys as English".
